# 초보자용 설명 주석 달기

사용자가 지정한 코드 파일에, 코딩을 막 배우는 사람이 읽어도 흐름을 따라갈 수 있도록 설명 주석을 추가한다.
목표는 "주석만 읽어도 이 파일이 무엇을 하고, 각 부분이 왜 필요한지 알 수 있는 상태"다.

## 진행 순서

### 1. 대상 파일 확인
- 사용자가 지정한 파일 경로를 확인한다. 경로가 없거나 애매하면(같은 이름 파일이 여러 개 등) 어떤 파일인지 먼저 물어본다.
- 여러 파일을 지정하면 한 파일씩 순서대로 처리한다.
- 파일 전체를 끝까지 읽는다. 일부만 읽고 주석을 달면 앞뒤 맥락을 잘못 설명하기 쉽다.
- 이 파일이 import 하는 같은 프로젝트의 다른 파일이 이해에 꼭 필요하면 그 부분만 가볍게 읽어 맥락을 파악한다. (그 파일에는 주석을 달지 않는다.)

### 2. 코드 이해하기 (주석 쓰기 전에)
주석을 쓰기 전에 아래를 머릿속으로 정리한다. 이해가 먼저여야 설명이 정확해진다.
- 이 파일의 역할은? (예: 화면 하나를 그리는 컴포넌트, 데이터를 변환하는 유틸 함수 모음)
- 실행 흐름은? 어디서 시작해서 무엇을 거쳐 어떤 결과가 나오는가?
- 초보자가 막힐 만한 지점은? (아래 "주석이 필요한 곳" 참고)

### 3. 원본 백업
- 프로젝트가 git으로 관리되고 있으면 백업 없이 진행해도 된다. (`git diff`로 언제든 비교·복구 가능)
- git이 아니면, 수정 전에 같은 폴더에 `원래이름.bak` (예: `App.tsx.bak`)으로 사본을 만든다. 주석 작업 중 실수로 코드가 바뀌어도 되돌릴 수 있게 하기 위해서다.

### 4. 주석 추가
원본 파일에 직접 주석을 추가한다. Edit 도구로 **주석 줄만 끼워 넣고**, 기존 코드 줄은 한 글자도 바꾸지 않는다.
(들여쓰기, 줄바꿈, 따옴표, 세미콜론까지 그대로 둔다. 초보자가 이해하려고 연 파일이 주석 때문에 동작이 달라지면 안 되기 때문이다.)

**① 파일 맨 위 요약 주석**
파일 첫 부분(단, `#!/usr/bin/env`, `"use client"`, `<?php`, 인코딩 선언처럼 맨 앞에 있어야 하는 줄이 있으면 그 다음)에 블록 주석으로 넣는다.

```
/*
 * ===== 이 파일은 무엇인가요? =====
 * (한두 문장으로 이 파일의 역할)
 *
 * ===== 전체 흐름 =====
 * 1. ...
 * 2. ...
 * 3. ...
 *
 * ===== 미리 알아두면 좋은 용어 =====
 * - 용어: 쉬운 설명
 */
```

**② 코드 사이사이 설명 주석**
- 설명하려는 코드 **바로 위 줄**에 단다. 줄 끝(인라인) 주석은 긴 설명을 담기 어렵고 원본 줄을 수정하게 되므로 피한다.
- 주석 들여쓰기는 바로 아래 코드 줄과 맞춘다.
- 함수·컴포넌트·클래스 시작 부분에는 "이게 뭘 하는지 / 무엇을 받아서(입력) 무엇을 돌려주는지(출력)"를 적는다.
- 큰 덩어리(섹션)가 바뀌는 곳에는 `// ----- 2단계: 사용자 입력 처리 -----` 같은 구분 주석을 넣어 흐름을 보여준다.

### 5. 검증
- 수정이 끝나면 파일을 다시 읽어 확인한다:
  - 기존 코드 줄이 그대로인지 (추가된 것은 주석 줄뿐인지)
  - 주석 문법이 올바른지 (주석이 닫히지 않아 코드가 주석 처리되는 일은 없는지)
- 백업(.bak)을 만들었고 git이 설치되어 있으면 `git diff --no-index 원본.bak 수정본`으로 `+` 줄만 있는지 확인하면 확실하다.

### 6. 결과 안내
사용자에게 짧게 알려준다:
- 어떤 파일에 주석을 달았는지 (링크로)
- 파일이 어떤 일을 하는지 한두 줄 요약
- 특히 공들여 설명한 어려운 부분 2~3곳 (줄 번호와 함께)
- 백업 파일을 만들었다면 그 위치와, 확인 후 지워도 된다는 안내

## 주석이 필요한 곳

모든 줄에 주석을 달면 오히려 코드가 안 보인다. 초보자가 "이게 뭐지?" 하고 멈출 곳에 집중한다.

**꼭 설명할 것**
- 처음 보면 낯선 문법: 화살표 함수, 구조 분해(`const { a } = obj`), 스프레드(`...`), 옵셔널 체이닝(`?.`), 삼항 연산자, 리스트 컴프리헨션, 데코레이터, 제네릭(`<T>`), async/await, 정규식 등 — 처음 등장할 때 한 번 자세히 풀고, 이후엔 짧게
- 라이브러리/프레임워크 기능: `useState`, `useEffect`, `map`/`filter`/`reduce`, `pandas.groupby` 등 — "이 도구가 해주는 일"을 설명
- 왜 이렇게 했는지 바로 안 보이는 로직: 조건문의 의도, 예외 처리 이유, 순서가 중요한 이유
- 매직 넘버·특수한 값: `300`, `0.8`, `'#1A73E8'` 같은 값이 무슨 의미인지 (코드로 추측 가능한 범위에서)
- 데이터가 어떤 모양인지: 객체/배열의 구조를 예시로 (`// 예: [{ id: 1, name: '상품A' }, ...]`)

**설명하지 않아도 되는 것**
- `i++`, `return result`처럼 그 자체로 명확한 한 줄
- 바로 위 주석에서 이미 설명한 내용의 반복

## 주석 문체

- **쉬운 한국어, 짧은 문장**으로 쓴다. 존댓말 "~해요" 체를 쓴다. (예: `// 버튼을 누르면 장바구니에 상품을 추가해요.`)
- **"무엇"보다 "왜"**를 함께 쓴다.
  - 아쉬운 예: `// count를 1 증가`
  - 좋은 예: `// 버튼을 누를 때마다 숫자를 1씩 올려요. 화면에 보이는 '좋아요 수'가 이 값이에요.`
- **전문 용어는 처음 나올 때 풀어 쓴다.** 영어 원어를 괄호로 함께 적으면 나중에 검색할 때 도움이 된다.
  - 예: `// 상태(state): 화면이 기억하고 있는 값이에요. 이 값이 바뀌면 화면이 다시 그려져요.`
- 필요하면 **일상 비유**를 쓴다. (예: "useEffect는 '화면이 다 그려진 뒤에 할 일'을 예약해두는 것")
- 확실하지 않은 내용은 단정하지 않는다. 코드만으로 의도를 알 수 없으면 `// (추측) ~를 위한 것으로 보여요.`처럼 표시한다. 틀린 설명은 설명이 없는 것보다 초보자에게 더 해롭다.

## 언어별 주석 문법

파일 확장자에 맞는 주석 문법을 쓴다.

| 언어 | 한 줄 | 여러 줄 |
|---|---|---|
| JS / TS / Java / C / C++ / C# / Go / Kotlin / Swift / Rust | `//` | `/* ... */` |
| JSX / TSX 의 JSX 태그 안쪽 | `{/* ... */}` | `{/* ... */}` |
| Python / Ruby / Shell / YAML / R / TOML | `#` | 여러 줄 `#` (Python 독스트링은 함수 설명에 사용 가능) |
| SQL / Lua | `--` | `/* ... */` (SQL) |
| HTML / XML / Vue·Svelte 템플릿 | `<!-- ... -->` | `<!-- ... -->` |
| CSS / SCSS | `/* ... */` | `/* ... */` (SCSS는 `//`도 가능) |

주의할 점:
- **JSX/TSX**: `return ( ... )` 안의 태그 사이에는 `//`를 쓰면 화면에 글자로 찍히거나 문법 오류가 난다. 반드시 `{/* */}`를 쓴다. 태그 밖(일반 JS 영역)은 `//`.
- **JSON**: 주석을 지원하지 않는다. 파일에 주석을 넣으면 파일이 깨지므로, 주석 대신 대화창에서 각 항목을 설명하고 그 이유를 알려준다.
- 블록 주석 안에 `*/` 문자열이 들어가지 않게 한다. (예: 정규식이나 경로를 인용할 때)

## 지켜야 할 것

- 코드 로직, 변수명, 포맷을 바꾸지 않는다. 버그나 개선점을 발견하면 코드를 고치지 말고 `// 참고: ~하면 오류가 날 수 있어요.`처럼 주석으로 알려주거나, 결과 안내에서 따로 말한다.
- 코드에 들어 있는 개인정보(이름, 전화번호, 이메일, 주민번호 등)나 비밀값(API 키, 비밀번호, 토큰)을 주석에 옮겨 적거나 결과 안내에 인용하지 않는다. "여기에 API 키가 들어가요"처럼 역할만 설명한다.
- 파일이 매우 길면(대략 500줄 이상) 핵심 함수와 흐름 위주로 주석을 달고, 반복되는 비슷한 코드는 첫 번째에만 자세히 설명한 뒤 "위와 같은 방식이에요"로 짧게 처리한다.
